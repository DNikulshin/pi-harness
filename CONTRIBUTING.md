# Как участвовать

Адаптер Pi для ядра `@dnikulshin/harness`. Здесь — короткий вход: что делать с идеей, как оформить
правку и что проверить до PR. Норматив процесса — [`AGENTS.md`](./AGENTS.md), история версий —
[`CHANGELOG.md`](./CHANGELOG.md).

## Идея или дефект

Работа идёт по issues: без issue нет ветки и PR. Шаблоны — при создании issue («Баг», «Задача»).

| Что у вас                                                                | Метки                              |
| ------------------------------------------------------------------------ | ---------------------------------- |
| Дефект адаптера (не запускается, `/cycle` падает, артефакты не читаются) | `type:bug`, `area:*`, `prio:*`     |
| Новая команда или поведение                                              | `type:feature`, `area:*`, `prio:*` |
| Инфраструктура, зависимости, рефакторинг                                 | `type:chore`, `area:*`, `prio:*`   |

**Дрейф контракта ядра — не дефект адаптера.** Если `/cycle` отказал из-за чужих полей или версии
схемы, это дефект контракта: issue заводится в
[DNikulshin/dev-harness](https://github.com/DNikulshin/dev-harness/issues) по правилу «сначала ядро,
потом адаптер» (`AGENTS.md`).

**Об уязвимости — не через issue:** порядок в [`SECURITY.md`](./SECURITY.md).

## Ветка

```bash
git switch main && git pull --ff-only
git switch -c feat/42-short-slug      # или fix/, chore/, docs/
```

Префикс — по типу задачи, в имени — номер issue и короткий латинский slug. Ветка от актуального
`main`: устаревшая база даёт конфликт, а GitHub на конфликтующем PR **не запускает проверки
вообще**.

## Коммит

`<type>(<scope>): <что сделано>`; детали — в теле: почему так и что отвергли.

- один коммит — одно логическое изменение;
- ссылка на issue — в теле PR (`Closes #42`), не в коммите;
- closing-слово (`closes`/`fixes`/`resolves` + номер) **в сообщении коммита тоже закрывает issue**:
  GitHub разметку там не разбирает, пример с чужим номером закроет чужую задачу.

## Проверки

```bash
node --version        # 26.13.x: engines.node = >=26.13 <27
npm ci
npm run check         # node --test + tsc --noEmit + prettier --check
npm run test:e2e      # нужна сеть: живой прогон на ядре из реестра
```

- новое поведение — с тестом (`node:test`); тесты не требуют установленного ядра — поддельный `bin`
  кладётся во временный проект (`test-support/fake-project.mjs`);
- `npm run test:e2e` в PR не блокирует, но красный E2E на закреплённой версии ядра — это ошибка
  адаптера, а не флейк;
- секретов в диагностике и тестовых данных нет: `.env*` и тела артефактов в issue не вставляем.

## Границы правки

| Не трогаем          | Почему                                                          |
| ------------------- | --------------------------------------------------------------- |
| `types/`            | генерируется `npm run typecheck:types`                          |
| `package-lock.json` | только осознанное изменение зависимостей, отдельным коммитом    |
| `node_modules/`     | установленные пакеты, не исходники                              |
| протокол цикла      | он живёт в ядре: здесь — потребление контракта, а не его правка |

**Никаких импортов ядра.** Только `bin`-команды (`harness-*`), `.pi/harness.version` и
`.pi/artifacts/**`; запрет проверяется `test/imports.test.mjs`. Новая runtime-зависимость — только с
обоснованием: сейчас их нет.

## PR

- заголовок как у коммита; тело: что сделано, почему так, как проверять, `Closes #N`;
- обязательные проверки: `checks (ubuntu-latest)`, `checks (macos-latest)`, `pr-references`;
- мерж в `main` — squash, делает владелец; версия в npm неизменяема, поэтому релиз идёт отдельным PR
  с поднятием `version` в `package.json` и разделом в `CHANGELOG.md`.
