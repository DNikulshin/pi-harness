# AGENTS.md — pi-harness

Адаптер Pi для ядра `@dnikulshin/harness`: переносит в код то, что раньше держалось на дисциплине
модели — регистрацию команды `/cycle`, чтение `cycle-driver next`, запуск гейтов, показ состояния и
артефактов, подтверждения владельца на переходах.

Ядро — внешний пакет. Здесь нет ни одной его внутренней строки: ни `scripts/**`, ни
`scripts/lib/**`.

## Границы

| Что                    | Как                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Обращение к ядру       | только `bin`-команды (`harness-cycle-*`, `harness-*`) и файлы `.pi/` (`.pi/harness.version`, `.pi/artifacts/**`) |
| Импорт ядра            | запрещён; проверяется `test/imports.test.mjs`                                                                    |
| Совместимость          | `peerDependencies["@dnikulshin/harness"]`; несовпадение — отказ с обоими номерами, код 1                         |
| Правки протокола цикла | только в ядре (`DNikulshin/dev-harness`), здесь — потребление контракта                                          |
| Управление стадиями    | за CLI ядра; адаптер показывает и подтверждает, но не подменяет `cycle-state`                                    |

## Команды

| Команда             | Что делает                                   |
| ------------------- | -------------------------------------------- |
| `npm test`          | `node --test`: тесты модулей и контракта CLI |
| `npm run typecheck` | `tsc --noEmit`: строгая проверка JS + JSDoc  |
| `npm run format`    | prettier                                     |
| `npm run check`     | тесты + `tsc` + проверка форматирования      |

Отдельный обязательный чек `pr-references` (`pr-checks.yml`) проверяет ссылку на issue в теле PR:
`tooling/pr-reference.mjs`, тесты — `test/pr-reference.test.mjs`. HTML-комментарии, блоки кода и
`Closes #N` в обратных кавычках ссылкой не считаются: GitHub внутри кода ключевое слово не
распознаёт, и зелёная проверка там означала бы issue, закрытый руками (так вышло с #4).

CI (`.github/workflows/ci.yml`) гоняет `npm run check`, проверку совместимости и `npm run test:e2e`
на **закреплённой** версии ядра: красный PR значит ошибку адаптера. Ночной `nightly-e2e.yml` гоняет
тот же E2E на `latest`: красный значит дрейф контракта в ядре. Смешивать эти два сигнала нельзя —
иначе непонятно, что именно сломалось.

Фикстура E2E (`test-support/consumer.mjs`) требует окружения, которое легко забыть:
`cycle-state init` считает `base_sha` от ветки `main` (`git rev-parse --verify main`), поэтому в
фикстуре создаются и `main`, и ветка задачи; `issue.json` пишется снимком, потому что `criteria`
читает критерии из `### Готово, когда` тела issue, а в реальном цикле этот файл готовит супервизор
(`gh issue view N --json title,body,labels`).

## Релиз

Версия в npm неизменяема, поэтому публикуется собранный архив, а не репозиторий:

1. PR поднимает `version` в `package.json` и добавляет раздел в `CHANGELOG.md`.
2. Мерж в `main` (squash) и тег `vX.Y.Z` на `main` после зелёного CI — тег публикует
   (`release.yml`).
3. Порядок внутри workflow: гейт «`NPM_TOKEN` задан» → `npm run check` → `npm run test:e2e` →
   `npm pack` → `tooling/check-package.mjs ... --tag "$GITHUB_REF_NAME"` →
   `npm publish ./dist/*.tgz --provenance --access public`.

Состав архива проверяется до публикации (`tooling/package-contract.mjs`, тот же список проверяет
`test/package-contract.test.mjs`). Цели `bin` проверяются с битом исполнения: без него `npx`
отвечает 126/127 — это уже ловили в CI на скелете.

## Правила

1. **Стиль — JS + JSDoc, строгий `tsc`.** Типы не «для галочки»: `checkJs` включён, `strict`,
   `noUncheckedIndexedAccess`.
2. **Новая зависимость — только с обоснованием.** Сейчас runtime-зависимостей нет: разбор версий
   (`src/compat.mjs`) написан свой, потому что диапазон объявляем мы сами.
3. **Никаких импортов ядра и его путей.** Если чего-то не хватает — это дефект контракта ядра,
   заводится issue в `DNikulshin/dev-harness`, а не обходится чтением внутренностей.
4. **Отказ лучше догадки.** Неизвестный диапазон, битый `.pi/harness.version`, нечитаемая версия —
   внятная ошибка, а не «наверное, совместимо».
5. **Секреты не печатаем.** Диагностика не содержит содержимого `.env*` и тел артефактов.
6. **Работа по issue.** Ветки `feat/*`, `fix/*`, `chore/*`, `docs/*` от `main`, имя содержит номер
   issue; коммит и push — только в рабочую ветку задачи, `main` защищён.
7. **Ссылки — ссылками.** Issues, PR, ADR и другие адресуемые документы упоминаются markdown-ссылкой
   (`[PR #17](https://github.com/DNikulshin/pi-harness/pull/17)`), а не номером: номер сам по себе
   перехода не даёт. В сообщении коммита и в имени ветки ссылку вставить некуда — там номер
   остаётся.

## Связь с ядром

Контракт, который адаптер потребляет: `docs/release.md` (публичный API, версии) и Приложение A
`docs/orchestrator-core.md` (схемы артефактов) в репозитории ядра. Порядок правок — «сначала ядро,
потом адаптер»: релиз ядра с изменением контракта, затем PR здесь.
